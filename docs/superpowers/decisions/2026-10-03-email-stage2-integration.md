# Stage 2 integration decisions

Email stays a declarative isolated Worker with generic host controls. Its private capabilities, exact account scope, immutable saved payload, and unknown-outcome fences remain independently enforced by the host and provider service.

## Settings content

An optional bounded preferences node uses the same renderer, global node/byte limits and governed event channel as the main view. It appears in the existing native Settings Preferences tab. Duplicate IDs between preferences, main content and navigation are rejected. Losing authority hides and retires preferences; it provides no alternate state or credential access. Email explicitly declares an encrypted signature preference, with an explicit insertion edit and the existing 30-day retention ceiling. Signatures are never injected by Send.

## Static Worker size

The real minified Stage 2 Worker reached 69,302 bytes after reusing the shared closed HTML grammar and adding triage, original source and preferences. Deleting the honest indexed fallback or duplicating a weaker parser would reduce product correctness. Raise only the immutable Worker-source bound from 64 KiB to 96 KiB, consistently in Kit/package validation and Web session validation. The total artifact remains bounded at 128 KiB; event/response/render limits and all private-data limits are unchanged. Test one byte over the new source bound. This is a static executable packaging allowance, never additional runtime authority. Rollback is the prior Web/API/Kit package and Email version, with existing data retained.

## Release distinction

The unchanged-authority UI-only release is 1.6.0-stage2.1. Full Stage 2 integration package is 1.6.0-stage2.2 and requires exact new capability and data review. Passing component or fake-provider tests does not mark Stage 2 complete. Normal supported UI dispatch, Linux lifecycle behavior and final rendered evidence remain acceptance gates.

## Reviewed provider modification permissions

Existing account bindings identify Send and request read/send only; they cannot authorize mailbox mutation. Stage 2 requires two independent checks before requesting broader Google or Microsoft permissions: an operator-configured account capability and the host's current reviewed action membership. The generic host projects optional `reviewed_action_keys` from active same-version, same-grant owner action bindings anchored to the same resource, with registration, descriptor, epoch and deadline fences. The Email adapter maps `triage_message` to `modify` and `permanent_delete_message` to `permanent_delete`; absence of the optional projection preserves existing read/send behavior. Browser or module input cannot supply this authority.

Automatically expanding every read/send connection was rejected because it changes existing grants. Inferring authority from a broad cached Google token was rejected because provider permission does not establish current Deft approval. Explicit module capability ceilings plus the generic reviewed-action projection are the smallest adequate change: the host remains provider-independent and existing contracts remain compatible.

Gmail modification requests `gmail.modify`; immediate permanent deletion separately requires `https://mail.google.com/`. The demo Stage 2 cutover requests modification only. Microsoft uses `Mail.ReadWrite`, with separate local capability ceilings and `Mail.Send` still required for send. Granted capabilities are the intersection of reviewed capabilities and actual returned scopes; refresh reduction and current authority revocation deny further use. Triage asks for the exact token operation instead of borrowing read authority. Sources: https://developers.google.com/workspace/gmail/api/auth/scopes and https://learn.microsoft.com/en-us/graph/permissions-reference.

Acceptance includes unchanged read/send authorization URLs, exact new scope requests, partial consent, refresh scope reduction, broad tokens unable to add unreviewed capabilities, revoked triage review denying provider I/O, and a supported UI consent/triage/Undo path. Pure OAuth tests pass 33/33, including these capability boundaries; host projection and real-provider acceptance are recorded separately. Rollback retains the prior package, private configuration and original custody paths; new scopes never silently become authority in an older deployment.

## Scoped service bulk request budget and deadline

Actual SDK fixtures measured a 25-message Gmail labels Run at 1,371 Runtime requests with provider refresh, including 1,367 heartbeats. Rich Send with one PDF takes 24 requests, or 32 with provider refresh. Two concurrent maximum-size triage Runs, two refreshed Send Runs, and four managers polling every 10 seconds require 2,830 requests per minute. The demo operator explicitly sets the existing `DEFT_APP_RUNTIME_RATE_LIMIT_PER_MINUTE` deployment option to 3,200; its peer-based key, authentication, payload limits and authority checks remain unchanged. The default remains 90 in source. Preserve the previous environment value for rollback. The default budget failed the fixture before mailbox writes and cannot support the reviewed bulk size.

Pacing these requests at 90 per minute would exceed the initial 60-second lease and child timeout. A deterministic fixture with 50 ms SDK latency and 200 ms provider latency expired after 14 mutations despite successful lease heartbeats. Triage therefore gets a local wall limit of 300 seconds, capped by the authenticated technical session expiry. Before claiming triage, the manager renews any technical session with 320 seconds or less remaining: the wall budget plus the existing 15-second SDK claim bound and 5 seconds for local dispatch. Newly issued sessions must satisfy that same minimum. Send retains its existing 60-second renewal rule and wall cap. The manager passes the expiry as a separate strict IPC scalar, leaving the SDK credential closed to session ID/token. The child rejects missing, malformed, expired or inconsistent session metadata. Initial claim and Start leases must still be current; every existing heartbeat, provider/custody fence, revocation check and unknown-outcome journal boundary remains in place. Caching successful authority or dropping nested checks was rejected.

Acceptance requires renewed triage leases to continue safely beyond the initial 60 seconds, renewal of cached technical sessions before their remaining lifetime shortens the wall budget, denial at the technical session or 300-second deadline, immediate revocation denial at the next boundary, and no replay after an uncertain provider effect or acknowledgement. The supervisor deadline and unchanged rich/PDF Send tests pass 19/19; runtime bulk/deadline fixtures and actual Linux child/browser/provider evidence are recorded separately. Synthetic timing and call-count proofs do not establish real-provider latency or normal UI completion. Rollback restores the prior code/configuration after stopping managers and preserves the latest shared owner pair, custody, journals and unknown latches.

## Saved Send snapshot and connected custody capability ceiling

Live rich Compose saved and reopened correctly but both saved-snapshot requests returned409. Human-action capture uses exact current Send authority and a connect-purpose source projection that does not contain optional connection reviewed_action_keys. Refiltering the configured custody ceiling through that absent optional field removed modify, so the connected read/search/thread/send/modify record no longer matched its nominated binding and became reauth_required.

The payload builder now reads the exact already configured connected custody binding to build MIME/From. It never begins OAuth, obtains tokens, admits modify/delete, sends, or mutates custody. Exact current owner/App/version/grant/Send runtimebinding/target pins and actual connected Send capability remain mandatory; account identity continues to come solely from encrypted custody. Connection begin/callback still filters optional capabilities through individually current reviewed_action_keys. Using broader connection admission or weakening custody equality was rejected. Independently authorized reads already use their existing custody nomination and remain unchanged.

Focused regression reproduces the original authority-denied failure with stored modify ceiling and omitted optional review keys, then verifies saved Send capture succeeds with no provider calls or custody changes. A configured permanent-delete ceiling with partial provider consent also cannot force new/fullmail consent merely to build Send; exact pin changes and revoked resource authority still reject. This does not create a permanent-delete binding. Filechooser extension access is separate from the saved-snapshot409.

## Historical terminal Activity and inaccessible drafts

The owner-scoped historical Run-status endpoint correctly returned terminal metadata, but the Worker then attempted to mark its associated older incompatible draft submitted. That draft read returned APP_STALE, making the successful status check appear unavailable and preventing explicit terminal Activity cleanup. The historical draft schema/access gate must remain unchanged, and no operator API deletion may bypass the normal product action.

The actual bridge masks private-state errors, so treating a generic unavailable response as historical staleness would conceal other denials. After matching terminal Run metadata, consult the existing governed current-version draft list first. When the associated draft is absent from that visible list, preserve it without reading, marking or deleting its unavailable payload. List failures remain failures; a listed draft follows its normal read and CAS marker path. Fresh exact terminal Run-status remains mandatory before removing the saved Activity copy. Draft marker-write staleness, CAS conflicts, unrelated read denials and pending/unknown/mismatched Runs still fail; request deletion uses its existing CAS. The UI identifies preserved drafts and explains that removal permanently deletes the saved Activity copy and an accessible unshared submitted draft while keeping the core Run receipt and mail. Broad suppression of state errors was rejected because it could conceal failed authority or concurrent writes. Automatic cleanup was rejected because removal is irreversible and must remain explicit.

Regression acceptance covers terminal metadata persistence with untouched incompatible draft bytes, fresh terminal-only removal, no provider admission, and refusal of marker writes/CAS/permission/session errors. This version/artifact-only Worker patch changes no declaration, quota, retention, provider scope or host contract. Live supported UI acceptance is required before claiming completion; rollback retains old package, bindings, ciphertext and journals.
