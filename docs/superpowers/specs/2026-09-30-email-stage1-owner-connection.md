# Stage 1 owner connection contract

Status: partially implemented in the local preview.60 / Email 1.5.9 candidate. The authenticated host callback and exact-purpose module adapter are implemented; the new member admission, persisted consent and setup UI are undergoing integrated verification. No live member Gmail connection or automatic supervised refresh is certified. Existing module OAuth/custody tests and UI fixtures do not prove those journeys.

The intended outcome is that an eligible human member connects and reconnects their own account under an already reviewed App deployment, sees verified account health, and can end their own access. Deployment review, private owner consent, provider consent and authorization of each external action remain separate boundaries. Core remains generic; Email owns account/provider identity, OAuth behavior and credential custody.

## Baseline before owner opt-in

The legacy host has exact private target custody, but combines deployment review with private owner setup. These observations motivated the explicit opt-in branch; the legacy mode keeps these restrictions:

- `AppResourceSyncManagement.reviewer` and `assertManager` in `apps/api/src/lib/app-resource-sync-management.ts` require owner/admin. `prepareConsent`/`activateConsent` use the authenticated reviewer as `owner_user_id`; `revokeConsent` also uses this reviewer gate.
- `manager`/`reviewContext` in `apps/api/src/lib/app-runtime-management.ts` require owner/admin and resolve an anchored action against `actor.actor_id`. `loadRuntimeOwnerTarget` in `app-runtime-owner-target.ts` checks exact organization, owner, installation, version/grant and operator through current resource custody.
- `loadLiveAttachmentSyncBindingAuthority` in `app-attachment-sync-authority.ts` requires the private owner to remain owner/admin, and requires resource/registration review identity to match that owner. The legacy resource reader has the same role restriction. A route-only change cannot make member custody live.
- `enforce_app_runtime_registration` and `enforce_app_runtime_binding` in `packages/db/upgrades/0.3.0-preview.31-app-runtime-channel.sql` require an active owner/admin reviewer. Resource binding review identity is tied to its private owner by preview.37 and the current schema. New member semantics require matching persisted authority and DB admission changes.
- `ResourceSyncClaimSchema` in `packages/app-kit/src/resource-sync-client.ts`, inherited by Sync v3, does not attest `owner_user_id`, `target_key` or Email account `authority_epoch`. A deployment map nominates a mapping; it is not fresh authority.
- `/api/connections/:provider/connect` and `/callback` in `apps/api/src/routes/connections.ts` deliberately return404. Retired native OAuth is not an integration path.

## Decision

Use an explicitly reviewed **owner connection policy**, a narrow current-authority projection, and a governed module adapter. Extend the existing App review, private resource/runtime custody and session boundaries; do not add a general credential framework, parallel connection registry in core or new service infrastructure.

| Option | Consequence |
| --- | --- |
| Adapter over existing manager setup | Smallest transitional wiring for current owner/admin-owned bindings; cannot satisfy normal member setup. |
| Reviewed opt-in owner connection policy and projection | Recommended: separates deployment review from consent to an individual owner's target, with explicit compatibility and DB fences. |
| General OAuth/credential framework | Adds abstractions and operations before a second consumer requires them; does not remove the member-consent gap. |

The opt-in policy is part of the reviewed package/effective grant, pinned to its version, package/grant digest and lifecycle. It declares an exact private resource, allowed action keys and maximum consent duration. Eligible roles are fixed by the host to active human owner/admin/member; package authors cannot add guest or agent eligibility. A separate admin-reviewed admission fixes the deployment operator and resource limits. The deployment-owned adapter registry fixes provider code/configuration and exact account pins. Opt-in is absent by default. A member cannot choose another owner or operator, deploy code, enlarge retained media/fields, or approve deployment changes through connection setup.

New opted-in custody rows carry an immutable reference/digest to that reviewed policy, covered by preparation/activation digests and DB guards. Existing rows retain their existing review mode. Preserve owner/admin deployment review; the opted-in private consent reviewer is the authenticated private owner. Action activation must likewise distinguish deployment admission from the private owner's exact target consent, while retaining current action uniqueness and external-write review policy.

## Small interfaces and trust flow

The numbered sections describe the required semantics. The current host implements `/api/app-owner-connections/:installationId/context`, admin admission review/activate/revoke, and owner resource/action review/activate. The owner request contains the admission reference and exact requested consent/action; the host supplies owner, organization, operator and deployment identity. The default-off `DEFT_APP_OWNER_CONNECTIONS_ENABLED` flag gates the new path. Action permissions are independent options and are not all prerequisites for account connection.

This does not yet automate deployment-owned provider registry entries for arbitrary new member targets. The controlled demo still needs exact operator-configured account/binding pins. Ownership-only teardown after expired consent, supervised refresh and the broader two-account journey remain required; do not describe resource admission alone as a connected Gmail account.

1. **Owner setup review/activation.** An authenticated web call nominates installation and target. The host derives organization and owner from the exact current web session, loads the opted-in reviewed policy and fixes operator/adapter from deployment authority. Its review covers descriptor/limits, target, version/grant/lifecycle, operator, policy digest and consent expiry. Activation rederives the same values under existing lock order and creates exact owner-private custody. Input IDs never confer authority.
2. **Current source authority projection.** A trusted module adapter nominates resource binding and purpose. The host authenticates the caller independently and returns current organization/owner, installation/version/grant, target, binding/descriptor/policy identity, permitted operation, relevant session/attempt pins and a conservative expiry. Reuse the checks in `resourceSyncWebAuthority`, `loadLiveAttachmentSyncAuthority` and `loadRuntimeOwnerTarget`, with the explicit opt-in branch. Browser setup uses a current human SID; runtime reads use exact purpose-scoped resource credentials; an external action additionally requires its current authorized action/Run context. An ordinary Sync lease cannot authorize connect, remote grant revocation or Send.
3. **Governed module connection adapter.** Resolve only a deployment-approved adapter matching the reviewed installation/version/grant/policy. Core owns authentication, consent, target routing, bounded input/error contracts and safe callback dispatch. Email supplies `createEmailOAuth` from `examples/apps/email/providers/oauth-account.mjs`, configured server-side clients, fixed provider URLs and encrypted custody. Worker code or browser input cannot nominate adapter code, credentials, provider endpoints or redirects.

The Email adapter implements the existing `host.resolveAccount({scope,account_id,purpose})` and `host.assertAuthority({binding,purpose})` ports by combining fresh generic source authority with a durable server-owned Email mapping. That mapping fixes stable account ID/provider/connection target, exact resource/action bindings, reviewed capability ceiling and independent account `authority_epoch`. Reconnection advances the account epoch through reviewed mapping updates. Neither `runtime_epoch` nor custody `setup_generation` is that epoch. Do not put tokens in Experience state, browser recovery, ordinary module records or logs.

Begin derives scope and browser binding from the authenticated SID or a host-generated secure HttpOnly setup cookie. The cookie/state retains exact SID/owner/session expiry; callback rechecks the stored session without placing a bearer in a URL. Apply origin/CSRF protection, bounded parsing, initiation quotas, no-store/referrer policy and fixed local return navigation. The callback consumes the matching one-use state, rederives the same account/target/purpose and invokes Email verification/custody. A denied provider callback burns matching state; it cannot guess an account from an address, code or token claims.

Keep conservative deadlines through provider I/O, ciphertext persistence and lock release; recheck before returning identity or delivering a credential. The UI shows Connected only after verified provider identity, durable custody and current host authority succeed. Reviewed source status alone is not Connected. Provider scope reduction intersects the reviewed ceiling; OAuth success never authorizes an external write by itself.

Teardown uses a separate ownership-only path: the private owner can revoke custody and discard credentials after App/read consent expires, without regaining read or Send authority. Fence host access first and invalidate pending Email setup state; failed module cleanup stays denied and recoverable. Remote provider-grant revocation remains a separate explicit operation because its scope may exceed one local account. Preserve account identity continuity and other accounts' custody.

## Compatibility, migration and rollback

Add versioned opt-in policy/projection contracts and additive immutable policy references through the supported upgrade runner, with corresponding fresh-schema definitions and DB guards. Do not edit historical migrations, infer policy for existing rows, broaden existing grants or reinterpret old reviewer fields. Legacy primary targets, encrypted associated data, current owner/admin setup, Sync v2/v3 envelopes and direct human action contracts remain compatible; use a separate projection contract rather than silently extending closed Sync schemas.

Disabling the new policy/adapter path denies new setup and current projected access. Retain additive rows, receipts, encrypted identity/custody, one-use state tombstones and encryption keys for roll-forward. Do not delete account history or replay an uncertain provider exchange/refresh as rollback. Deployment-owned OAuth client registration and protected custody configuration remain explicit external prerequisites.

## Failure modes and acceptance sequence

1. Implement the policy and owner-consent boundary first. Actual HTTP/DB tests must reject wrong owner/tenant/target, guest/agent/foreign SID, unreviewed adapter/operator, stale policy/version/grant, increased limits and duplicate target actions; prove eligible member consent only for opted-in deployments and unchanged legacy manager behavior. Prove fresh DDL and supported upgrades, with no automatic old-grant expansion.
2. Implement and test the authority projection through the same host interface used by the adapter. Verify resource/action audience separation, exact binding/target/owner, purpose restrictions and absent opt-in denial. Hold DB/I/O boundaries while revoking membership, SID, target consent, runtime or grant; no identity, Start input or credential may escape after denial/expiry. Verify owner teardown after consent expiry independently of read authority.
3. Wire the existing Email OAuth module behind the governed adapter. Test state replay, browser/session mismatch, denied callback consumption, superseded setup, callback after disconnect, provider subject change, reduced scopes, lost response and delayed durable custody. Preserve `refresh_pending` before provider refresh; an uncertain result requires reauthentication, not an automatic repeat. Persist and recheck the independent account epoch.
4. Add the configured connection slot to host settings and inspect actual desktop/mobile, light/dark behavior, verified health, reconnect and independent disconnect. No fake connection success or credential entry into chat. Keep active Account and composer From identity visible.
5. Only after configuration and the real host journey work, execute the separately authorized two-account controlled-provider milestone. Fixtures do not prove real connection, delivery/Sent, outgoing files/MIME, or accepted-response-loss reconciliation. Those remain separate Stage1 exits.
