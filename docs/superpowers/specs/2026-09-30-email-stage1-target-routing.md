# Stage 1 target routing spike

The first journey needs two owner-private accounts in one installation, with independent current consent and exact action dispatch. Preserve legacy consumers, tenant isolation, current owner/binding checks and immutable operation history.

Use the existing private resource custody boundary as the host target rather than broadening the legacy `connected_accounts` provider uniqueness. Add a bounded reviewed `target_key` to resource custody, defaulting existing rows/sessions to `primary`. A target is nominated within owner/installation/grant scope; the key itself grants no access. Runtime bindings may anchor to an exact owner-private resource binding. Experience sessions pin one target key and expose only that target's resources and anchored actions. Unanchored legacy actions remain available only on the primary target.

This is smaller than a new parallel connection registry plus duplicated custody. It also preserves independently built Email/provider boundaries: the Email registry maps stable account identity to host target/resource/action references, while tokens stay with supervised provider custody. Removing the target selector would reintroduce the same ambiguity in every read/send caller. Do not use a key, address or provider name to select a first matching action.

Review/activation binds the selected resource target into the review digest. Current resource authority and owner are rechecked on action capture and claim. Changing target opens a new session and requires the appropriate existing consent; it does not mutate an existing reviewed session. Existing rows are backfilled to primary by additive column defaults; old non-primary consumers fail closed. Rollback disables new target creation/selection and retains new rows and receipts for roll-forward.

Action uniqueness is by organization, installation, version/grant, owner, target and action, rather than exact resource-binding ID. Two resource descriptors for the same account cannot claim the same action. Legacy unanchored actions cover the primary target and conflict with anchored primary actions; a new legacy registration conflicts with every anchored primary registration. Management holds the installation lock while checking and inserting. Both exposure and direct invocation reject multiple matches. Disabled registrations retain their slot until revoked. Another owner's explicitly anchored non-primary action is independent.

Private state visibility, browser recovery identity and encrypted associated data include the selected non-primary target. Primary preserves the historical associated-data and browser-key layout. Record UUIDs and the active-record/byte/tombstone budgets remain installation-wide per owner/state key: connecting accounts cannot multiply the existing quota. Adoption checks the aggregate budget while selecting only the current target's rows. Target columns and runtime anchors are immutable, with a composite organization foreign key protecting resource-binding references.

The host Source selector flushes dispatched inputs and settles dispatched state writes before opening a new session; a failed save keeps the current source. It is disabled while the current Email composer is open. This is adequate for the current host composer path, whose edits are persisted there. It is not a general save acknowledgement for future Worker-managed debounced editors; those need an explicit save/idle contract before enabling switching during editing.

Schema preview.57 was applied through the supported upgrade runner to an isolated database initialized with the prior 54-migration baseline, and through the fresh-schema runner to a separate unused database. Both report pgvector 0.6.0, 55 ledger versions, preview.57 exactly once and all four target fields/triggers. Existing populated pre-preview.57 draft adoption, destructive down migration and production restore are not certified by that DDL proof. Safe rollback disables new routing and preserves the additive schema and immutable historical outcomes for roll-forward.

Proof: fresh and supported upgrade schemas, two same-provider targets, exact owner/action routing, guessed foreign target denial, legacy primary compatibility, and revocation before confirmation/claim. DB tests must execute, not silently skip. This spike does not establish OAuth registration, supervised refresh, rich snapshots or real-provider sends.

The real HTTP target suite executes thirteen checks with zero failures/skips, including conflicts reproduced as HTTP 201 before the fix and HTTP 409 afterward, target-separated encrypted drafts, cross-target ciphertext substitution, aggregate quota, foreign owner/tenant IDs and revocation before confirmation/claim/start. Independent existing private-state and adoption HTTP checks also execute with zero skips.

Selected target consent deadlines are retained from the trusted runtime capture through Run matching, held secret reads, final kind/gate checks and transaction completion. A synchronous check immediately before the Start envelope denies expiry without plaintext disclosure, while retaining the earlier durable dispatch marker. The held-read and held-commit regressions reproduced HTTP200 and now return403. No caller-authorized deadline or new lookup is added; unanchored legacy actions retain their behavior.
